## Appendix B — Recommended GUIDELINE.md byte-preservation strategy (proposal — NOT implemented)

Status: documented for owner decision (Q-02). **No `.gitattributes`, hook, workflow or setting was created or modified by this review**; the strategy below awaits explicit owner approval before implementation.

### Observed damage vectors (evidence)
- Two independent scripted text-mode uploads normalized the archival CRLF bytes to LF: the primary-repository transfer (blob `19d0d46e`, 53,698 B) and the mirror's `new answer/` upload (`8b9e84b0…`); every loose mirror copy of the prompt file lost exactly 1,536 CR bytes (`68d4dee3…`, 37,645 B) (E-03, E-18, E-19).
- Plain `git add/commit/checkout` preserved the mixed-EOL bytes exactly (repair blob `5cf1fe00`, re-verified inside the Git object), and the early web-UI uploads preserved CRs (54,240 B variant, CR count 1536) — normalization is **transfer-path-dependent, not Git-inherent** (E-04, E-18).

### Layer 1 — prevention at the Git layer: `.gitattributes` (one line, when approved)

```
GUIDELINE.md -text
```

- `-text` disables all Git EOL normalization for that path on every clone/add/checkout/merge, regardless of any machine's `core.autocrlf`; diffs remain textual (the attribute affects EOL handling, not diffability).
- Must **not** be `GUIDELINE.md text eol=crlf`: the file has mixed line endings by design (LF wrapper text + CRLF archival region); `eol=crlf` would convert the whole file and corrupt it differently.
- Must **not** be combined with a blanket `* text=auto`, and adding it later must never be paired with `git add --renormalize`.
- Limitation: protects only Git paths — it would not have prevented either observed damage event (both were non-Git text uploads). Hence layers 2–3.

### Layer 2 — detection: two-layer checksum validation
1. Whole-file SHA-256 in `SHA256SUMS.txt` (recomputed whenever the wrapper text legitimately changes; staleness risk demonstrated by F-02).
2. The permanent **archival invariant**: extract the embedded prompt region and require SHA-256 `38634f573b0391402a1b58ad927d133fa0ad2ca6551c8ea66180daddd3e24b16` forever — it survives all legitimate document edits and is now physically anchored to the ZIP-member bytes verified in E-19. Reproducible check:

```sh
python3 - <<'PY'
import hashlib
d = open('GUIDELINE.md','rb').read()
b = b'<!-- BEGIN ORIGINAL MASTER PROMPT; SOURCE BYTES FOLLOW -->\n'
e = b'<!-- END ORIGINAL MASTER PROMPT; SOURCE BYTES END -->'
r = d[d.index(b)+len(b):d.index(e)].rstrip(b'\r\n')
ok = hashlib.sha256(r).hexdigest() == '38634f573b0391402a1b58ad927d133fa0ad2ca6551c8ea66180daddd3e24b16'
print('archival region OK' if ok else 'ARCHIVAL REGION CORRUPTED')
PY
```

### Layer 3 — procedure
- Transfer `GUIDELINE.md` (and the package generally) only by git-native push/clone — never via text-mode web/API uploads, ZIP tooling or editors that rewrite line endings on save.
- Run `sha256sum -c SHA256SUMS.txt` **and** the archival-region check after every transfer and at every documentation milestone; record results in `HANDOVER.md`/`CHANGELOG.md`.
- The owner keeps the offline original (`MASTER DEVELOPMENT PROMPT.txt` and/or the handoff ZIP) as the authoritative archival source.
- Automation (a CI check job) is deferred to Phase 3 and requires owner-approved workflows; until then the gate is procedural.
