# Architecture proposal — not implemented

## Scope and component diagram
```text
 Browser / Windows Agent ── HTTPS/WSS ──> [TLS Edge Windows service]
                                            ├──> [Next.js Windows service]
                                            └──> [API/WebSocket Windows service]
                                                       ├──> [PostgreSQL Windows service]
                                                       └──> [Worker Windows service] ──> devices
 Windows updater ── authenticated HTTPS ──> [separately hosted central Update Proxy]
                                                    └──> private GitHub Releases
 Operator workstation: browser ↔ interactive Local Desktop Bridge → allowed apps
 Checkout workstation: Agent Windows Service ↔ interactive Session Helper
 Optional separately deployed Linux Guacamole gateway ──> RDP/VNC/SSH targets
```
All browser access to the central service is remote over LAN; the local bridge is on the *operator's* interactive computer, not assumed to be on the central computer. The bridge must be explicitly installed per operator workstation if native launching is needed. Local browser/bridge communication requires a separately validated loopback origin and secure enrollment design; see security policy. Windows Session 0 cannot display interactive UI. The agent needs a separate, per-user session helper for checkout notifications; delivery may fail when no session is logged in and must be reported.

## Processes and responsibilities
* Independently supervised Windows services: TLS edge, Next standalone server, API/WebSocket server, workers and dedicated PostgreSQL cluster. Exact TLS edge/service-hosting components TBD; do not expose inner ports. Durable jobs in PostgreSQL, with transactional lease/claim, expiry, bounded retries, cancellation and idempotency. WebSocket delivery and job state are not tied to HTTP request lifetimes.
* Browser UI has no database credentials; API enforces all authorization. Agent identity is separately enrolled and restricted to its own device. Workers resolve secrets only for authorized tasks.
* The central service terminates HTTPS/WSS with an operator-installed certificate whose DNS name agents and browsers trust. Bootstrap, renewal, revocation and no-trust behavior need target testing. A self-signed certificate cannot simply be silently trusted.
* A Windows agent communicates outward with mutual TLS or equivalent per-agent credentials, pending enrollment threat-model approval; task signatures/nonces, scope, expiry, audit and replay protection are required. No generic command execution.
* For SSH use xterm.js in browser and server-side ssh2 with host-key verification, unique session authorization and an audited ephemeral session. Dangerous-command confirmation is best effort and not a security boundary: terminal input may be edited, encoded, pasted or generated by applications. RBAC, target allowlists and network policies are the controls.
* For RDP/VNC, propose native clients through bridge for Windows operator sessions, with simultaneous windows and application-side profile/session records. Browser-managed embedded remote desktops would need a separately deployed Linux Guacamole service (client and guacd), so not claimed as included. Credentials must not appear in arguments; feasibility of secure handoff per client is open. Session lifecycle observation and user expectations of in-browser tabs require proof of concept and approval.
* TeamViewer and Winbox launch interfaces depend on installed vendor versions. No password on command line; fail closed if safe handoff is unavailable. No claim of automatic login.

## Major alternatives
| Decision | Alternatives | Proposal and tradeoff |
|---|---|---|
| Runtime | serverless; Next custom server; independent services | Independent services simplify durable WebSockets and restart isolation; more service management. |
| Jobs | in-memory; external queue; PostgreSQL queue | PostgreSQL queue reduces services; requires careful claim/lease, recovery and tests. |
| Remote access | Guacamole on Linux/WSL; Windows native clients | Native bridge fits Windows without mandatory Linux; browser embedding and session control are not established. Optional Guacamole needs separate deployment and authentication design. |
| Database | bundled dedicated PostgreSQL; shared existing server | Dedicated bundled instance meets self-contained goal but adds patching and data lifecycle; external instance can be future optional mode. |
| Installer | WiX Burn/MSI; Inno Setup; MSIX | Conditional proposal WiX Burn/MSI: service and install lifecycle, upgrade control; complexity and rollback custom work. Inno simpler but lifecycle must be implemented; MSIX service/network/data constraints need validation. Final choice after prototype. |
| Secrets | plaintext/config; DPAPI machine; centralized KMS | DPAPI-protected AES key with dedicated service identity and protected backup is workable on Windows; restore to another machine requires an explicit key recovery mechanism. KMS is more scalable but adds infrastructure. |

## Version baseline
Agent targets .NET 10 LTS; supported patch and all exact Node, PostgreSQL, Next.js and package versions remain unselected. Verify OS/architecture and library compatibility before pinning. .NET support policy: https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core . Next standalone output still requires bundling a Node runtime and static assets: https://nextjs.org/docs/app/api-reference/config/next-config-js/output . Guacamole architecture: https://guacamole.apache.org/doc/gug/guacamole-architecture.html .

## Limitations and scale
No hardware, network, NVR, TeamViewer, Windows or browser compatibility has been tested. PostgreSQL indexing and bounded worker concurrency support growth; actual throughput and capacity require load testing. No fixed branch or device quantity. A router ping indicates router reachability only, not WAN/Internet health.

## Phase 2 revision — 2026-11-18 (owner decisions approved; implementation not authorized)

### Explicit service and process topology
The owner-approved production topology requires **five distinct Windows services** on the management host, each independently supervised by Windows Service Control Manager (SCM). The TLS edge, Next.js, API and worker must not be consolidated into a single service. The PostgreSQL service is a fifth service. A lightweight native service host may supervise each Node process where needed; the exact host and edge product remain unselected pending proof of concept. Each has its own restricted Windows identity and ACL; secrets only to authorized services. Never run them all as LocalSystem merely for convenience.

```text
 LAN browser ── TLS ──┐
 Agent ── TLS / agent identity ──┤
                               v
          [Edge service: TLS, WSS, routing, access limits]
                    ├── loopback ──> [Next service: UI/rendering]
                    └── loopback ──> [API service: auth, RBAC, HTTP, WSS]
                                          ├──> [PostgreSQL service: loopback]
                                          ├──> [Worker service: durable jobs]
                                          │        ├─ monitoring / ISAPI / SMB+SCM
                                          │        └─ package staging / agent dispatch
                                          └── SSH session manager ──> ssh2 ──> devices
 Operator browser ── paired, authenticated local channel ──> per-user bridge
                                                               └─ allowlisted native apps
 Checkout agent service ── authenticated per-session IPC ──> user-session notifier
 Optional separately deployed Guacamole/Linux ──> RDP/VNC/SSH targets
```

| Service | Responsibilities; dependency | Health and recovery |
|---|---|---|
| PostgreSQL | Dedicated application cluster and DB; no dependency on app | SCM running plus authenticated SQL readiness. Restart bounded/backoff on crash; stop restart loop and alert on corruption or failed storage. |
| API | Auth, RBAC, session/agent endpoints, WSS, inventory, vault orchestration and durable-job submission. Requires healthy DB for readiness; handles DB transient failure without accepting unsafe writes. | Liveness is process/event-loop check; readiness checks DB, migrations, key access and queues. WSS disconnect/reconnect, reject mutations when unready. SCM/host bounded restarts; don't mistake a live process for readiness. |
| Worker | DB-leased jobs: monitoring, deployment, NVR sync, retry and reconciliation. Requires DB and its own credentials/permissions. Agent dispatch via authenticated API/channel, not assumed direct shared memory. | Liveness plus DB lease loop, heartbeat, lag and stale-job metrics. Resume expired leases; side effects must be idempotent or explicitly reconciled. |
| Next | UI/rendering; API access through controlled edge route, no DB/vault credentials. | Liveness plus render/static readiness. Restart on failure; reject health if required assets absent. |
| Edge | Public HTTPS/WSS routing, certificate management and limits; listens only on configured interfaces. Backends on loopback. | TLS and upstream route probes; restart bounded; missing/expired certificate fails closed. |

Recommended startup: PostgreSQL -> DB readiness and schema compatibility -> API and worker -> Next -> edge. SCM dependency ordering is not application readiness: service entry points must retry with backoff and report degraded until their own readiness criteria pass. Startup should not automatically perform destructive migrations; installer/updater runs reviewed migrations with an exclusive lock before declaring readiness. Edge can start in maintenance mode while upstreams are unavailable if necessary; do not route unsafe traffic. SCM failure actions and process-host behavior must be tested on the target OS. No infinite restart storm.

On shutdown/update, edge rejects new requests and drains with deadline; API rejects new operations, closes or drains WSS, and persists task/session states; worker stops claiming, cooperatively stops jobs, releases leases where safe and records uncertain side effects for reconciliation; Next exits; database stops last after workers/API disconnect. Hard shutdown may interrupt work: expiry and reconciliation handle it on restart, not a claim of exactly-once execution. Configure structured JSON logs, severity, correlation/job IDs, event log/service health alerts, rotation and retention, clock synchronization and redaction. Restrict ACLs; no credentials, tokens, terminal transcripts or installer output containing secrets by default. Health endpoints must disclose no secrets and must not be publicly reachable without appropriate access controls.

TLS termination and agent mTLS need a coherent design: if edge terminates mTLS, it must validate device certificates and convey verified identity to API only over an authenticated, restricted local channel that strips all externally supplied identity headers. Otherwise use a separate agent TLS listener terminating directly in API. Do not treat arbitrary forwarded headers as identity; select and test one option before implementation.

### Monitoring and CCTV behavior
Worker scheduler persists due probes and claims them with leases, randomizes schedule to avoid bursts, limits global and per-network concurrency, and applies separately configurable interval, timeout, retry count and history retention. A completed probe records timestamp, router, latency, attempt count and classified outcome. Online means the configured router responded; offline means configured retries failed within known operational conditions; unknown means no valid recent observation, disabled/unavailable monitoring or indeterminate error. Avoid conflating ICMP filtering with physical disconnection. Branch detail shows retained history and fresh equipment statuses; configurable staleness, timezone and retention. WAN/Internet health is a separate future signal and must not be inferred.

CCTV discovery is **from explicitly registered/configured NVRs**, not unapproved subnet scanning. Select one NVR, branch or all; authorize and snapshot eligible targets. Choose an associated credential explicitly or follow an approved ordered policy; bounded attempts/lockout prevention, never log secrets. Establish validated transport (HTTPS preferred; insecure HTTP only by explicit policy), authenticate via an ISAPI method supported by that firmware, and fetch supported channel configuration plus runtime channel status with bounded timeout/pagination and response size. XML parser must disable external entities/DTD. Normalize channel IDs, camera identity/IP, status and vendor data; preserve raw evidence only if sanitized and retained under policy. Detect unsupported endpoints/auth, certificate/transport errors, permission, malformed data, partial response and firmware differences separately.

Reconcile each **complete successful** snapshot transactionally: upsert cameras by NVR + stable channel identity, update last seen/sync and interpreted online/offline/unknown; mark missing channels inactive/removed without deleting history. Never mark missing from partial/failed fetch. Duplicate/reassigned channel identity and channel reuse need explicit rules and tests. Persist each sync run, outcome and sanitized error; distinguish last attempt from last successful sync. Channel status is NVR-reported, not ICMP; unrecognized states map to unknown. DS-7732NI-K4 and DS-7732NXI-K4 compatibility and ISAPI endpoint semantics are not verified.

### Provider integration boundaries
SSH is performed by central API-hosted session manager, not by the bridge: validate target scope and host key, retrieve authorized credential server-side, multiplex tab/session identifiers, rate-limit output and protect against cross-user access; UI supports tab unread state, search, snippets, fonts, reconnect and fullscreen. Dangerous command confirmation is best-effort, not shell confinement. A reconnect must reauthenticate and revalidate host key. Do not log terminal content by default.

Winbox, TeamViewer LAN, native RDP and VNC use approved applications on the **operator workstation** via the bridge. Central service authorizes target/profile and issues a constrained capability; bridge validates application identity and supplies only validated target/options. Browser sessions on non-Windows machines need an alternative and are not implicitly supported by a Windows bridge. Multiple native windows are not equivalent to embedded tabs; track only launch/outcome unless actual session lifecycle is observable and tested. Credentials must not be passed as arguments, environment variables, URLs or browser responses. Supported OS-protected handoff may be used only after specific client/version testing and threat review; otherwise launch without credentials and require manual sign-in. No automatic TeamViewer/Winbox login is asserted. Optional Guacamole entails its own Linux service deployment, authorization, encryption and session audit; not part of the self-contained Windows package by default.

|---|---|---|
| Separate services | One host reduces service count but couples failures; many services add operational complexity | Owner-approved five services; Windows startup, account, crash and shutdown tests remain required. |

| Bridge transport | Browser extension/native messaging gives OS-scoped IPC but install/extension friction; loopback HTTPS simplifies browser call but adds certificate/origin/local-process risk | Prefer native messaging with managed extension + named pipe/ACL; browser compatibility and pairing PoC mandatory; no generic listener. |

| Installer | WiX Burn/MSI, Inno Setup, MSIX | WiX candidate, not final, after clean offline VM install/upgrade/rollback and dependency licensing tests. |
| PostgreSQL | Dedicated bundled instance vs external/shared instance | Dedicated cluster for standalone deployment; validate Windows service identity, upgrades and backup. |
| Agent | Framework-dependent vs self-contained .NET | Self-contained .NET 10 LTS; validate actual Windows versions and patch servicing. |
| Remote | Native clients vs Guacamole | Native conditional baseline; embedded web UI requires separately evaluated gateway. |

## Owner-approved topology and service lifecycle — 2026-11-18
The five separate SCM services are **mandatory**, not an open architecture decision. The separately hosted central Update Proxy is a distribution service operated by the owner, not a sixth mandatory service on every installed management computer; it must not contain its private-repository secret in the installer or installed application. It is not implemented. All account names, ports and components below are proposed deployment parameters to validate, not claims about the target environment.

```text
 Operator browsers / agents ── HTTPS/WSS ──> [Edge: public LAN port only]
                     ┌─────────────────────────┴─────────────────────────┐
                     ▼                                                   ▼
           [Next UI: loopback]                              [API + WSS: loopback]
                                                                         │
               [Worker: no listener] ←── durable jobs ──> [PostgreSQL: loopback]
                                                                         │
 Installed updater ── authenticated TLS ──> [Central Update Proxy, separate host]
                                                │ server-side GitHub App credential
                                                └── private GitHub Releases (fixed origin)
 Operator workstation: Browser ↔ paired Bridge (interactive user) → approved apps
 Checkout workstation: Windows Agent service ↔ Session Helper (interactive user)
```

| Service | Payload, identity and privilege | Startup, dependencies, communications, ports |
|---|---|---|
| PostgreSQL | Bundled PostgreSQL binaries; dedicated restricted virtual/local service account, rights only to its own data/log paths; not local/domain admin; SCM logon-as-service. DB application/worker roles have least SQL privileges, separate controlled migration/admin role. | Automatic; start first; TCP loopback only (installation-configured, e.g. 55432, avoid conflicts); no inbound firewall exception. SQL authenticated readiness, data directory and version compatibility before API/worker. |
| API/WebSocket | Bundled Node runtime + compiled API, supervised by Windows service-compatible host; dedicated restricted identity with DB app role, DPAPI/vault key ACL and only required network/service rights. | Automatic after DB service starts; readiness retries authenticated SQL and verifies schema/key and WSS readiness. Loopback HTTP/WSS internal port e.g. 13001; edge-only routing; no inbound firewall exception. Authenticate service peers independently of loopback. |
| Worker | Bundled Node + worker/service host; separate restricted identity with DB worker role and narrowly delegated outbound rights; explicit credentials for SMB/SCM from vault under audited, scoped operation; no blanket domain admin service identity. | Automatic after DB service; readiness verifies DB, migration version and lease loop. No inbound port; outbound restricted for permitted NVR, ICMP, SMB/SCM and edge/API calls. SCM start order alone does not establish dependency readiness. |
| Next | Bundled Node + standalone server and traced dependencies/static/public assets; restricted web identity; no DB or vault access. | Automatic; API may be degraded independently; loopback internal port e.g. 13000, no inbound firewall exception. Ready only when server and required assets respond; API requests routed via edge. |
| Edge | Bundled proxy executable + service wrapper if needed; restricted dedicated identity with read access to TLS private key only, no vault/DB role. | Automatic after web/API have started, probe readiness independently; TCP 443 example configurable and explicitly allowed only for management LAN. Only externally exposed application listener. Trusted certificate/hostname required. Health is TLS and routing availability, not merely process alive. |

Ports are examples, not fixed assignments. Internal HTTP bind loopback plus restrictive service-to-service authentication; local processes can reach loopback, therefore use short-lived service credentials with restricted ACL or mutually authenticated IPC, strip external forwarded identity headers, validate agent identity at termination and integrity-protect identity assertion to API. Edge must not rely on user-supplied identity headers. Worker has no listening socket. PostgreSQL authentication remains mandatory even locally. Edge routes `/` to Next and defined API/WSS paths to API, checks size/time/rate limits and never exposes PostgreSQL or administrative endpoints directly; exact routing and local IPC need Windows PoC.

SCM dependencies express ordering only; readiness gates DB schema compatibility/key access and probes before traffic and dispatch. Keep edge in authenticated maintenance/degraded mode if a dependency is not ready, never signal healthy because a process merely runs. Bounded exponential restart with alert and capped failure actions; operators resolve persistent startup errors instead of infinite restarts. All services structured-log to ACL-protected files/Windows event log with bounded rotation, UTC timestamps and correlation IDs; no secrets, terminal contents or uncensored external output. On normal stop, edge drains, API rejects new work and drains WSS, worker stops claims and journals in-flight tasks, Next stops, then DB checkpoints and stops; deadlines and recovery on forced kill are explicit. During upgrade maintenance blocks new operations, verified backup precedes locked migration, and order reverses for shutdown and follows readiness for restart; rollback retains versioned binaries and restores compatible DB/key backup if needed. Installer/repair re-registers only owned service configuration and health-checks; uninstall stops/removes only owned services/binaries and leaves data/config/backups by default. Do not silently replace accounts, cluster data, secrets or certificates.

### Update Proxy boundary
The owner-approved proxy is separately operated and accessed via authenticated TLS. The installed application/updater uses its own authorized client identity; its web browser does not receive GitHub tokens or raw private repository responses. Proxy authenticates server-side to a narrowly installed GitHub App using short-lived installation tokens, keeps the App private key only in a protected server-side secret store, and never packages it in clients. It exposes only allowlisted repository/channel/release assets and authenticates/authorizes every manifest and download request. Full threat model, cache control, incident response and signing limitations: SECURITY_POLICY.md and DEPLOYMENT_WORKFLOWS.md. Deployment host, networking and owner/operator of this additional service remain **technical deployment questions**, not an invitation to replace the chosen proxy architecture.
