# Versioning policy — owner-approved bootstrap; design not implemented

## Scope and exception
Every pushed source commit on every supported branch needs a unique traceable application version and an independent pipeline attempt. Owner approved a **one-time initial installer bootstrap exception**: while no commit produces a genuinely installable and runnable application, bootstrap commits run available validation/documentation pipelines and receive unique immutable versions, but need not publish an application installer or successful application release. Do not fabricate artifacts. The objective end is the **first commit demonstrated by an independent clean Windows test to install offline, start the application and required services, pass health checks and function as a real application**, with a complete standalone package and mandatory relevant gates. That exact commit is the transition point and receives the first real tested installer and Release. If the first apparently installable commit fails gates, publish nothing; correct the failure and test again without claiming the exception has ended successfully. Once transition succeeds, the exception is permanently closed: every eligible later commit including documentation-only, maintenance and all temporary branches must run the full installer/release pipeline; failed mandatory checks publish no successful Release or installer.

## Identity, branch, channel and source rules
A **distinct Git commit SHA has one globally unique immutable application version**; tags `v<version>` point to that exact SHA. `main` versions are stable SemVer `M.m.p`; `beta` prereleases `M.m.p-beta.N`; temporary branches use sanitized identifier plus branch-name hash and unique number `M.m.p-<branch>-<hash>.N`. Version, channel, full commit hash and build ID appear consistently in UI/backend/agent/installer/manifest/release as applicable. Build-generated manifest is authoritative release metadata, sourced from checked-in version intent and commit classification; never write a version commit back to Git. Conventional Commits govern feature/breaking/maintenance increments, docs and chore changes get at least patch-compatible increments. MSI numeric encoding versus SemVer and agent internal version mapping require validation.

**PROPOSED — OWNER CONFIRMATION REQUIRED: one original channel per commit SHA.** The same SHA may become reachable from many branches but would not receive a new version, second channel or duplicate release. Under this proposal, the first successful immutable registration assigns its source branch/channel; branch creation from an existing tip does not reclassify history. Pushing an already registered SHA to another channel triggers an isolated audit/validation run for that ref, which must not publish a conflicting channel release. To promote beta to main, or otherwise release in a different channel, require a distinct new merge/squash commit; a fast-forward channel change must fail the channel policy check and be corrected with a new commit. Temporary branch names are bounded and normalized; append a hash of the original name to avoid collisions. Simultaneous first observations in different channels are ordered by an atomic registration ledger; ambiguous events fail closed and require review, never guessed. A branch push that contains multiple previously unregistered commits dispatches one isolated pipeline per commit; earlier already-registered commits retain their existing identity. Introduced parent histories must be traversed fully and attributed deterministically; do not silently exclude eligible commits. Merge commits themselves get versions. Deletion events have no new source commit. Force-pushes are prohibited on protected branches; elsewhere detect them, reconcile reachable/previously accepted commits, report missing ancestry and never rewrite tags or silently skip a previously eligible commit.

## Allocator, races and recovery
A durable transactional authority/ledger must atomically assign unique source identity, channel, version and monotonic allocation sequence, with unique constraints on full SHA and version; serialize stable semantic allocations and publication ordering. Treat Git tag creation as a separate idempotent remote action: compare-and-create, verify exact SHA, never force-update, quarantine any pre-existing conflicting tag. Use outbox/lease, atomic source claim, crash recovery and compare-and-swap, not a lossy GitHub Actions concurrency group. Independent jobs run in isolated workspaces with unique run IDs. GitHub API refs are a possible component, not yet demonstrated to provide required protected multi-record atomicity; do not claim a chosen store is reliable until validated. Reservation persists on failure; the version is burned and cannot be assigned to another SHA. A retry for the same SHA reuses the original reservation, records a distinct attempt and cannot change a published asset. If output differs from an existing published artifact, fail closed. Tag/version collisions, out-of-order stable completion, event gaps, webhook outages, runner quota and dispatch errors must alert and reconcile; do not cancel earlier builds. Concurrency cannot guarantee progress during GitHub outages, but intake and durable reconciliation must enumerate and attempt every eligible commit after recovery. A push trigger or failed attempt is **not** a successful build or release.

The proposed approach for one independent pipeline per commit is an intake event plus one separately dispatched workflow run per eligible source commit, not by assuming GitHub emits one event per commit. Verify GitHub event delivery, history traversal, dispatch refs, authorization and crash behavior end-to-end. No automatic version commits; workflows listen to branch pushes/controlled dispatch, not tag pushes, and publishing must not recursively trigger release generation. No current implementation or successful test exists.
