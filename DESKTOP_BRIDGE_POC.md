# Desktop Bridge — bounded future proof-of-concept specification

**Status: owner selected a PoC; execution is not authorized or performed.** No production bridge, generic command endpoint or irreversible system change is part of this phase. Obtain separate explicit approval for the isolated validation task.

## Scope and environment
Use disposable, snapshotted Windows VMs with non-production accounts, no real credentials, isolated DNS/network, representative supported browser and vendor client versions. Select native messaging + managed extension as initial candidate and compare authenticated loopback HTTPS; evaluate browser support and privileged provisioning. Install only allowlisted PoC binaries and mocked target services, with fake secrets and explicit user consent. Cleanup restores VM snapshot and removes extension/host pairing. Do not disable Defender, UAC, SmartScreen or firewall. Record exact Windows/browser/client version, test scripts, logs and limitations.

## Candidate prototype contract
1. Provision pinned central test origin/server public key through OS/admin-controlled install; verify out of band. Bridge generates per-user key; server binds enrollment to authenticated user and installation via one-time short-lived confirmation and proof-of-possession. No reusable enrollment secret in logs or URL. Confirm user and origin visibly; support explicit revoke, expiry and re-pair.
2. Browser extension checks exact scheme/host/port and top-level sender via browser origin rules; reject untrusted/opaque/nested origins. Native messaging host is per-user/session; ACL-protected named pipe or equivalent verifies Windows user/session/process. Compare loopback design's binding, CORS, host validation and DNS-rebinding behavior; Origin or loopback alone is insufficient.
3. Server issues short-lived signed single-use operation capability bound to bridge public key, user/session, allowed origin, exact target, operation, nonce and expiry. Validate signature and audience, redeemed atomically online or persist replay cache across restarts, reject expired/revoked requests; never embed passwords. Confirmation displayed in interactive session. Log authorized and rejected events without secrets.
4. Allow only fixed operations for Winbox, TeamViewer LAN, RDP, VNC and optional native SSH. Map operations to administrator-approved absolute canonical binary paths with pinned identity or verified publisher and protected ACLs; reject traversal, reparse/path replacement, writable binary paths and unexpected files. Direct process creation with per-app strict typed arguments; no shell, arbitrary arguments, paths, scripts, command lines or process launcher. Validate destination scope against token; no password in CLI/environment/URL.
5. Evaluate client-specific documented secure OS-protected handoff using synthetic credentials only, with cleanup and process inspection. If unavailable or unsafe, only manual login is supported; no automatic login claim. Record whether multiple sessions and lifecycle can be observed, without equating separate windows to embedded tabs.

## Adversarial and functional acceptance criteria
* Correct authenticated pairing and permitted target launch works for each tested application/version; unconfigured/uninstalled or changed executable fails closed.
* Cross-origin iframe, foreign extension, null origin, DNS-rebinding/host-header attack, local unauthenticated process, cross-user/session caller and token stolen for different bridge all fail. Replay across process restart, expiry, revoke, duplicate concurrent requests and altered signed payload fail. Verify service-side authorization and audit for every attempt.
* Malicious host/port, argument injection, shell metacharacters, path traversal, symlink/reparse substitution, writable-path binary replacement and requests for unapproved executable never execute. User refusal causes no launch. Test host shutdown/restart, token expiry and recovery.
* Inspect process arguments, environment, extension messages, files, IPC and logs for fake secret leakage; credential handoff passes only if vendor-supported and independently verified. Unsupported handoff is documented as manual login, not a passing automatic-login feature.
* Capture test evidence, versions, commands, negative results and cleanup; pass only for exact tested client/OS/browser combinations. A successful PoC is not production security approval. Review residual same-user local malware risk, key revocation and threat model before any production design approval.
