# Deployment workflows — design only

> **Current implementation status (0.1.223): the offline payload and read-only inspection are development fixtures, not an installer; mutating installer, database initialization/bootstrap/migration and orchestration are disabled. No unattended production deployment or release is authorized. See [README](README.md).**


## Agent via SMB and remote service control
Target one, selection, branch or all registered computers using explicit domain credential selection (GIG clients; OKCS checkouts). Check name resolution/transport, authenticate, ADMIN$ access, remote service-control permissions, existing version/hash, package integrity and required upgrade; transfer to unique staging path, verify, stop and backup existing, install, restart, verify service plus outbound identity/heartbeat. Per-device and per-step status and precise actionable error, bounded concurrency/retry, durable job, audit, continuation policy. No trust relationship or WinRM required. Existing service account privileges, firewall and administrative shares must be verified on real systems. Never put credentials in shell or process args; use supported credential APIs and avoid process-wide conflicting SMB connections, test isolation.

## Package deployment and Store Commerce
Upload with safe filename and folder, malware controls and size cap, calculate trusted source digest, select targets, authorize, create date-based destination, copy, compute destination digest, compare and bounded retry, report each step and continue per policy. Capture an immutable explicit operator approval before any force-close, with warning about data loss and coordination of open transactions. On target check connectivity; check process; send graceful close; wait bounded configurable time; force only after explicit approval and verify stopped; notify interactive user through agent helper when possible and record delivery result; locate the exact installer; execute fixed `Hyper.StoreCommerce.Installer.exe install` with elevation; capture sanitized stdout/stderr/exit code; verify version from a validated supported source; audit all steps. Arbitrary installer execution is high risk: allowlisted package provenance, strict folder/path validation and authorized approval required. No notification guarantee without active user.

**Owner-approved canonical destination:** `C:\Source\Package\<YYYY-MM-DD>\` only. The operator-provided Package Folder Name is an identifier/metadata field, never a nested directory. Record the exact target destination in the job and reuse it to locate `Hyper.StoreCommerce.Installer.exe`; never reconstruct the path from the identifier. Conflicting earlier lookup wording is superseded by the owner decision.

## Application installer and update
Conditional WiX Burn bootstrapper + MSI proposal, not yet selected definitively. Bundle pinned Windows Node runtime, Next standalone files/static assets, backend/worker, Windows service host, PostgreSQL Windows binaries, migrations, .NET self-contained components and legal notices. No developer tool or internet download needed at install. Choose all dependencies/redistribution terms after research. Installer must support administrator privilege, fresh install, health checks, repair, upgrade and uninstall. Store program files in versioned Program Files; data/config/backups under ACL-protected ProgramData; dedicated least-privilege accounts and services. Dedicated PostgreSQL cluster loopback only, initialization and service identity verified. PostgreSQL minor patches tested, major upgrades separately orchestrated with backup/restore or pg_upgrade, never automatic destructive data conversion.

Updates: select channel explicitly and use the owner-approved central Update Proxy; installed applications contain no reusable GitHub credentials. Resolve manifest by channel, enforce monotonic version/channel and prevent stable-to-beta absent consent. Download, validate hashes and TLS, stage immutably; hash does not authenticate publisher. Take verified recoverable backup of DB, settings, relevant data and separately protected encryption key; quiesce workers/services, migrate under lock, start and health-check. On failure, revert binaries if schema-compatible; otherwise restore consistent backup or perform vetted forward recovery, clearly state rollback can lose writes since backup. Do not promise zero-loss rollback or guaranteed availability. Record all operations. Package and updater must not overwrite data on uninstall; default retain data and give explicit separate deletion option with confirmation. Validate failed-install recovery and restore before production. Private GitHub access, bootstrap credentials, manifest authenticity, CA, disk space and OS support remain open.

## Detailed checkout package and Store Commerce state sequence
Precondition: explicit authorized operator identifies immutable package, exact folder and selected checkout(s), branch/all scope, concurrency and continuation policy. Validate folder name (single safe path component), archive extraction paths, package file size/type and approved provenance; store source SHA-256 and job snapshot. Record the local-operator coordination acknowledgement, warning that force-close risks open transactions/data loss, and explicit force-close approval before dispatch; approval must be scoped to package, targets and expiration.

For each target: (1) probe target and agent freshness; (2) create validated destination under approved root; (3) copy to job-specific temporary location, retry only within configured bound; (4) compute destination hash on target, compare to immutable source hash, retry mismatch within limit and report both hashes; (5) stage/promote file without overwriting unrelated data. Use the recorded date-only destination, never a nested package-name directory. (6) detect Store Commerce process and interactive sessions; (7) ask per-session helper to display `Please do not open Store Commerce. The application is being updated.`, record acknowledged/displayed, undeliverable or unknown honestly; never replace with dashboard-only message; (8) request graceful close and wait configured interval; (9) if still running, force-close only if the specific preapproval is valid and report action; (10) verify process stopped or fail safely; (11) resolve approved fixed installer filename within staged folder without path escape; (12) launch the fixed `Hyper.StoreCommerce.Installer.exe install` with required elevation through a predefined agent task, no arbitrary commands/arguments; (13) capture stdout/stderr with size limits, redaction and exit code; (14) verify installed version from supported tested sources and report mismatch/unknown; (15) emit green success or red failure for each step, timestamps, retries and final target summary. Report skipped steps distinctly; do not represent unknown notification delivery as success. On interruption reconcile installer/process state before retry to avoid duplicate execution. Continue other targets only per approved policy. Never silently kill a process.

## PostgreSQL and installer operational proposal
Install program binaries under versioned `Program Files`; store cluster/config, uploads, logs and backups in separate restricted `ProgramData` paths. A dedicated low-privilege Windows identity owns the cluster data and PostgreSQL service; app has a separate restricted DB role, migration role is elevated only for controlled operations. DB binds loopback and does not trust arbitrary local users; authentication and service credentials require secure provisioning without CLI secret exposure. Avoid modifying existing PostgreSQL instances. Preflight CPU/OS compatibility, storage capacity, privileges, existing service/port conflicts, filesystem ACLs and required OS components; no internet/developer tool dependency after package download. PostgreSQL licensing/distribution terms and required OS redistributables must be verified.

Fresh install: stage/check all payloads; register DB service, initialize cluster with protected credentials, configure ACL/auth and loopback; start and verify DB; create app roles/database, apply reviewed migration under exclusive lock, configure TLS and identities; install app services with failure recovery; start in dependency order and verify readiness. On failure stop new services and revert installation changes; retain any existing data. Initial cluster cleanup requires explicit safe ownership check and no user data, otherwise leave for recovery.

Upgrade: verify manifest and publisher trust policy, stage complete immutable version, confirm disk space, quiesce jobs, take consistent DB/file/config/key backup and test backup accessibility, migrate with lock, start and health-check, commit version only on health success. PostgreSQL minor patch binary replacement and major migration/pg_upgrade or backup restore need separate tested scripts and explicit compatibility plan; no silent destructive DB changes. Keep old binaries and backup until retention period and verification. If failure, roll back application only if compatible with current schema; otherwise restore verified consistent backup and communicate the recovery point and any post-backup write loss. Restore database, matching app files/config and protected vault key; test on another machine and document DPAPI portability/recovery. Uninstall stops services and removes binaries/registrations but leaves database/user data and backups by default; separate explicitly confirmed data deletion and key retention decisions required. No unconditional claims that failure leaves system usable without tests and available recoverable backup.

## Owner-approved date-only destination and collision handling
Each target stores deployment date, operator-provided Package Folder Name as metadata only, package SHA-256 and exact canonical `C:\Source\Package\<YYYY-MM-DD>\` directory. Transfer the package files directly to that directory; **never** create a package-name subdirectory. Record exact files and relative names, source/destination digest, job and target. Use restricted unique temporary files in the same date directory then verify and safely promote under a per-target/date lock. If another package already owns the same filename with a different digest, fail and ask for an operator decision rather than overwrite; reuse identical verified content only under explicit policy. Track full paths and ownership; clean up only job-owned temporary files. The installer is resolved against the recorded directory and must match the approved package manifest and hash; no inferred folder reconstruction.

## Central Update Proxy flow
Authorize an operator and selected installation/channel in the app; app/updater authenticates as its own installation to the separately hosted proxy over TLS. Proxy validates identity, entitlement and channel, retrieves allowlisted GitHub metadata via its server-side GitHub App, maps it to an approved manifest/asset, checks version monotonicity and streams only a verified asset. Updater verifies the received bytes against manifest hash, stages, snapshots a consistent recoverable backup, locks migration, drains five services, applies reviewed migrations, starts in dependency/readiness order and audits result. Stable cannot silently switch to beta or downgrade; recovery rollback is explicit and audited. A GitHub outage/expired proxy identity yields retryable classified error or approved fresh cache, never missing-auth bypass. See SECURITY_POLICY.md for authenticity limits and cache revocation. No GitHub secret is shipped to clients.
