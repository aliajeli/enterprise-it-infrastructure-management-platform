# Release process — design, not configured

## One-time bootstrap exception
The owner approved an initial bootstrap period before an installable application exists. Every bootstrap commit still has a unique immutable version and runs applicable isolated validation/documentation checks; it need not publish an installer or Release. Never issue a fake installer. The exception ends at the first source commit proven by an independent clean Windows test to install offline, start required services and a real runnable application, pass readiness and mandatory relevant gates, and yield the genuine standalone installer and matching GitHub Release. From then on no documentation, maintenance or feature commit on any supported branch is exempt from full validation, installer build and release. Failed gates never publish a successful release or installer. VERSIONING_POLICY.md defines transition and identity rules.

## Per-commit flow and publication
1. Protect `main` and `beta`; temporary branches are short-lived. Author changes on beta/temporary branches and review promotion. Intake every branch push, enumerate every eligible newly introduced commit, and reconcile missed events through durable history records; one independent pipeline run per source commit, unique version/channel reservation and fresh isolated runner. Existing commit identities are immutable. **PROPOSED — OWNER CONFIRMATION REQUIRED:** treat cross-channel SHA reuse as a policy violation requiring a distinct promotion commit; see VERSIONING_POLICY.md. Never assume one push event equals one commit.
2. Independently checkout full SHA and verify provenance, reservation and classification. Least-privilege build job, pinned action versions, dependency locks, secret scanning and isolated temporary workspaces. Untrusted code must not have publication credentials.
3. Run mandatory Tier 1 automated checks and Tier 2 actual Windows installer/upgrade checks per testing strategy; Tier 3 applies when integration changes and before claiming that compatibility, not to unrelated changes. Run lint, typecheck, unit, DB/API/WebSocket/security/agent protocol/deployment simulations, production app/agent build, installer creation, content and checksum validation. Installer must run clean offline Windows tests, preserve data and support upgrade/repair/uninstall/rollback; failure blocks successful publication. Where a required runner or check is unavailable the release fails or remains pending, never passes by omission.
4. Assemble exact tested assets: `Platform-<version>-windows-x64-setup.exe`, optional agent ZIP, manifest JSON (schema, version, channel, full SHA, build ID, sizes, asset SHA-256, compatibility), `SHA256SUMS.txt`, factual release notes and license/SBOM as applicable. Include all runtimes, static assets, services, PostgreSQL and required redistributables; do not require end-user developer tools or online package installation. Final filenames/platforms depend on validated packaging.
5. Publisher uses narrowly scoped credentials only after all gates. Atomically create/check exact-SHA `v<version>` tag; a pre-existing conflicting tag is an error. Create draft, upload all assets, re-fetch and validate size/hash/manifest, then publish `main` stable or `beta`/temporary prerelease. Never overwrite a tag or published release. Draft is not a successful release; clean up or reconcile partial drafts without exposing them as complete. Never trigger further pipelines from tag publication or write automatic version commits.
6. Proxy syncs only approved published releases with server-side GitHub App credentials, checking channel/asset/manifest policy, cache and access authorization (SECURITY_POLICY.md). Installed application receives no GitHub secret. SHA-256 is integrity only; publisher signing is separately planned and not verified.

## Reliability, retry and recovery
Use a durable event/commit/version ledger and independent run per eligible commit. Do not use a GitHub concurrency group as a lossy global queue; serialize allocation and stable publication with a reliable transactional authority. Record state intake → reserved → building → gated → draft → published or failed; implement idempotent transitions/outbox and lease recovery. If duplicate push or rerun arrives, reuse same version and compare exact SHA; never mutate published artifacts. Different result for a published version, collision, failed check or unauthorized channel fails closed. When GitHub, runners, proxy or credential provisioning are unavailable, emit actionable failure, preserve logs, and reconcile missing events and draft states when service returns; delivery and no-loss guarantees require tested infrastructure. No release is available merely because a workflow was triggered. Initial/current pipeline, builds and GitHub private releases are not verified in this session.
