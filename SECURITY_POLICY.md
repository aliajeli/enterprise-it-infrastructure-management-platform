## Proposed controls

## Credential Vault implementation status — 2026-11-19

### Implemented cryptographic core (not production-wired)

`apps/api/src/security/credential-vault-crypto.ts` implements a versioned AES-256-GCM envelope format:
- A fresh cryptographically random 256-bit data-encryption key (DEK) for each credential.
- Independent 96-bit random nonces and 128-bit GCM tags for secret encryption and DEK wrapping.
- Authenticated additional data (AAD) binds the envelope to its credential ID, branch ID, asset ID, credential kind, format version and key version. Copying ciphertext to another asset/branch or changing bound metadata must fail authentication.
- The 32-byte key-encryption key (KEK) is obtained only through the `CredentialKeyProvider` interface. The API has no plaintext environment-variable, file or hard-coded key fallback.
- Key version IDs allow old KEK versions to remain available for decrypt during rotation while new records use the active version.
- Decryption returns one generic failure and does not log plaintext or cryptographic material. Temporary key/plaintext buffers are zeroed on a best-effort basis after use.

### Mandatory production gates — still NOT implemented

1. A Windows DPAPI-backed provider bound to the dedicated service identity and machine, with restrictive filesystem/registry ACLs and no LocalSystem/domain-admin assumption.
2. A separately held recovery export protected by an independently controlled recovery key; documented custody, rotation, emergency access and a successful clean-machine restore drill. DPAPI machine-bound material alone is not recoverable after host loss.
3. A persistent key-version registry and rotation procedure that never destroys a key version while records still depend on it.
4. A database credential record and API layer with ADMIN-only management. The owner-approved role matrix explicitly denies OPERATOR stored-credential use; VIEWER is read-only. No credential values may be returned to browser responses.
5. Transactional audit of create/update/disable/reveal/use/rotate/recover actions, secret redaction and backup/restore validation.

The current key provider exists only as an interface. Unit tests use an in-memory test provider; this is test scaffolding, not a deployable key store. The module is not registered in the API, no credentials are persisted, and no live equipment credentials should be entered. Do not enable discovery until all mandatory gates pass.

## Local Desktop Bridge: concrete proposed protocol
**Trust model:** central management origin has a configured HTTPS origin (scheme, host and effective port, exact match; no wildcard/subdomain assumptions). Bridge resides in the logged-in operator's Windows session; a remote browser cannot contact a bridge on the server. Prefer a managed browser extension + OS native-messaging host over a browser-exposed network listener. Verify extension ID and host registration with administrative deployment; named-pipe IPC uses restrictive user SID/session ACL and verifies the connecting process/token. Browser extension receives messages only from configured exact application origins via browser-enforced externally-connectable settings and independently checks sender frame/top-level origin; reject unrecognized/null/file origins, unexpected frames and changed origin. These controls require browser-specific testing; CORS or `Origin` alone is not authentication.

**Pairing:** an administrator provisions the central server certificate/public-key trust and origin through an authenticated, integrity-protected local installation/configuration channel. Local user explicitly initiates pairing, sees server fingerprint and origin and confirms. Bridge generates a per-installation key in user-protected storage; register its public key with a short-lived one-time pairing request bound to authenticated application user, machine/session and explicit approval. Server verifies possession challenge and stores bridge id/key; revoke or re-pair upon device loss or key changes. No reusable pairing token in logs or URLs. Trust bootstrap before first pairing is an unresolved implementation gate, not TOFU masquerading as secure enrollment.

**Request:** browser makes normal authenticated, CSRF-protected API request with target, operation and selected bridge ID. API applies RBAC, target policy and audit, then signs a short-lived single-use capability containing issuer, exact audience/bridge id and public-key binding, user/session, exact origin, operation, target/port, client app id, request id/nonce, issued/expiry and key id. No passwords. Bridge verifies signature against securely provisioned server trust, key binding, origin, short expiry with bounded clock skew, operation schema and current user/session; an atomic replay cache rejects duplicate request IDs through expiry. API capability issuance is audited. Bridge returns authenticated result with same id; local user sees explicit confirmation for each sensitive launch. Restart must not erase unexpired replay protection; persist consumed IDs in ACL-protected storage or use online atomic redemption. Enforce rate and payload limits. Revoke bridge/user/session and reject new capabilities; a locally cached capability remains usable until expiry unless online redemption is required, so use online redemption for high-risk actions. A local process with the same Windows user privilege may still attack browser/bridge; additional isolation and executable integrity require threat-model and penetration testing.

**Launch:** accept only enumerated operations (`winbox.open`, `teamviewer.lan`, `rdp.open`, `vnc.open`) and typed host/IP, permitted port and nonsecret profile IDs. Verify target belongs to the signed authorized capability. Resolve and canonicalize administrator-configured absolute executable paths; prevent traversal/reparse-point substitutions, writable-path binary replacement and untrusted executables through ACLs, verified file identity/publisher or pinned hash as approved. Call a process API directly with a fixed argument schema (no shell, scripts, cmd, PowerShell, arbitrary executable, arbitrary flags, URLs or user-provided command string). Never accept remote path to executable. Restrict launch environment/current directory and avoid secrets in process arguments, files, environment and URLs. The bridge cannot turn an SSH-like terminal into arbitrary process execution. Record user-visible outcome, no secret data.

**Credential handoff:** capability contains no credential. The default for native clients is manual login. Any later automatic handoff requires client-specific documented OS-protected mechanism, target scoping, short lifetime, cleanup and threat-model approval; if unavailable, fail closed or launch without automatic credentials. Never claim existing RDP/Winbox/TeamViewer/VNC secure handoff without testing installed versions. Bridge compromise, local admin rights, DNS rebinding, malicious extension/origin, replay, token theft, spoofed target and argument injection must be tested.

## Owner-approved central Update Proxy — threat model and design
Trust boundaries: (1) authorized installed application to proxy over TLS with hostname and certificate verification; (2) proxy to fixed private GitHub API and release asset hosts via controlled server-side GitHub App identity; (3) protected proxy secret store, immutable cache and publication policy; (4) privileged release pipeline. The proxy is external to the installed application. No GitHub PAT, App key or reusable repository secret ships to application, installer, browser, or agent. A machine client uses its own provisioned, revocable application identity scoped to that installation; browser users authenticate through their application session, and the application enforces update RBAC. A browser session cannot itself authorize a different installation. Proxy checks client identity, allowed installation/channel and asset on every request, not just index requests; revocation invalidates cached authorization. Bootstrap, issuance, renewal and revocation of this distinct installation credential and stable proxy endpoint need owner/operator and TLS provisioning design.

Proxy only reads a fixed allowlisted repository, GitHub release IDs/tags, channel and approved immutable asset records; it never accepts an arbitrary download URL, arbitrary upstream host, unvalidated redirect, file path or credential. Redirects are checked at each hop against configured HTTPS GitHub release/CDN hosts with DNS/IP and egress restrictions, strict timeout, size limit and no internal/private metadata access; do not forward GitHub Authorization to third-party redirected hosts. Map signed-in app clients to server-side approved records; no raw GitHub metadata exposed. Stable may update only stable; beta requires explicit choice and authorization; temporary branches are prerelease and never offered as stable. Reject downgrade and implicit channel change; track installation version/channel with anti-rollback policy and explicit audited exceptional recovery. Avoid lexicographic SemVer comparison.

The proxy retrieves and validates release manifest/schema, exact tag/SHA/channel/asset name, file size and SHA-256 before serving a completed immutable cache object, and compares manifest/asset to release approval; generation/version identity prevents cache collisions. Size/total resource limits, streaming limits and atomic temp-to-cache promotion prevent incomplete downloads and DoS. Rate-limit by authenticated installation and IP, bound concurrent downloads, record structured sanitized audit of identities, decisions, channels and digest; never log credentials, bearer tokens, URL query secrets or browser session contents. Conditional revalidation (ETag or bounded TTL) and authenticated GitHub webhook signals or polling synchronize newly published releases, but webhook signature verification and replay protection are mandatory. Cache entries keyed by immutable release/asset digest; atomically refresh metadata, invalidate revoked/unpublished releases and authorization grants immediately after verified sync or administrative revocation, fail closed if policy freshness exceeds approved maximum. Webhook outages trigger bounded polling and alerts.

If GitHub is unavailable or App credentials expire, return a classified error with retry-after; serve a cached approved asset only when authorization, policy freshness and configured cache validity still hold, otherwise fail closed. Do not fabricate latest versions or silently downgrade. Maintain health alerts, credential lifecycle and documented manual sync. Compromise of proxy or GitHub write access can substitute both checksum and payload: HTTPS plus SHA-256 provides transport/integrity, **not publisher authenticity**. Plan offline-controlled release signing keys with pinned public trust anchors, signed versioned manifests, key rotation and revocation; future Authenticode must be verified on Windows. No authenticity claim until implemented and independently tested. Obtain separate approval before enforcing a new signing prerequisite.

### Service identities, keys and incident response
Separate restricted Windows service identities and DB roles; no blanket LocalSystem/domain-admin. Vault data uses per-record AES-256-GCM with unique nonce and authenticated metadata, envelope key protected by DPAPI; PostgreSQL storage itself is not automatically encrypted by the vault. Enable separately approved volume/backup encryption (e.g. OS managed encryption) and test backup restoration. DPAPI-protected machine/service key is not portable: secure encrypted recovery export with separately held recovery key, rotation, emergency access and restore drill are mandatory before production. Protect service logs and DB backups with ACL and retention.

For suspected secret, signing, agent or bridge compromise: restrict access, revoke affected installation/agent/bridge/GitHub App credentials and keys, disconnect sessions, stop release distribution as appropriate, preserve redacted audit evidence, rotate affected secrets, review potentially altered releases and notify owners. Re-provision identities using trusted out-of-band channel; resume only after verification. Never assume token revocation fixes data already exfiltrated.

## Windows DPAPI helper primitive — 2026-11-19
A fixed-purpose .NET 10 helper and Node.js binary-IPC client now provide a DPAPI machine-scope primitive for 32-byte KEKs. The helper derives optional entropy internally from a domain separator, installation identifier and current Windows SID; it accepts no command-line arguments and uses no shell, environment secrets or temporary plaintext files. Windows CI builds the helper and runs a DPAPI round-trip/installation-binding test. This does **not** constitute a production key provider: service identity provisioning, installer-owned ACLs and ACL verification, persistent keyring/version registry, atomic rotation, independent recovery export and clean-host restore drill remain absent. Keep credential persistence and live use disabled.


The initial Windows integration test exposed and corrected a framing assumption: DPAPI-protected blobs are variable length, whereas the decrypted KEK is exactly 32 bytes. The Node protocol parser now applies those distinct bounds. Exact-head CI is required before treating this helper primitive as verified.


The DPAPI protocol now distinguishes input/output sizes: Protect accepts a 32-byte KEK; Unprotect accepts a bounded variable-length DPAPI blob and returns exactly 32 bytes. The Windows integration test is the acceptance gate for this protocol.
