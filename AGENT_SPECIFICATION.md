# Windows Agent — proposed

Standalone C# .NET 10 LTS self-contained Windows Service (no SDK/runtime prerequisite), automatic startup, least privilege compatible with required administrative tasks. Connect outbound HTTPS/WSS; independently reconnect with capped exponential backoff and jitter. No dependence on WinRM. Enrollment, unique identity, authenticated server, revocation, replay protection and clock-skew handling require design validation; insecure bootstrap is not acceptable.

Send heartbeat, status, installed version, executable and package SHA-256 with defined scope and system metadata. Offline/unknown thresholds must distinguish stale data. Collect registry uninstall entries in relevant 32/64-bit machine and accessible per-user scopes; investigate supported Store Commerce/Hyper.Commerce sources; explain incomplete coverage and scan errors. Do not invoke slow MSI reconfiguration via Win32_Product. Task protocol uses allowlisted, versioned typed schemas, bounded arguments, authorization, idempotency, timeout, sanitized output and execution audit. Never execute arbitrary PowerShell or shells.

Service is in Session 0. Interactive notifications require a separately deployed signed/unsigned-as-applicable per-user helper in the actual user's session with authenticated, ACL-protected IPC; report no active session or delivery failure and do not assert it was displayed. No bypass of UAC or security controls.

Installation and upgrades: preflight, detect installed service/version and hash, stage package, verify integrity and trusted transport, controlled stop, retain rollback copy, replace, verify, restart, compare reported version/hash and server connection. Define actual binary file hash vs package hash. Installer/Agent repair and rollback must be tested on power interruption. Local logs redact credentials and include bounded rotation. Unsigned builds warn normally; no signature bypass. Authenticode readiness is planned, not implemented.

## Identity lifecycle — proposed protocol, no implementation
1. **Bootstrap trust:** provision the central TLS CA/hostname through a protected deployment package or local administrator-controlled installer. Out-of-band verification of CA/public key and integrity/authenticity is required; SHA-256 fetched alongside an unsigned package is insufficient. If trust cannot be established, stop enrollment.
2. **Enroll:** authorized server creates an expiring, single-use enrollment ticket scoped to the registered computer, deployment job, approved server and deadline. Agent generates a new asymmetric private key on the target, non-exportable Windows key store where supported, with ACL limited to service identity. Transfer ticket through secured SMB/admin path with restricted ACL; never logs/command line. Agent validates server TLS, submits ticket, device public key and nonce/proof of possession; API atomically consumes ticket and verifies intended device/job, key proof and allowed lifecycle. An operator must review conflicts. Server issues unique short-lived certificate or equivalent asymmetric per-agent credential. Ticket alone is insufficient to prove hardware identity; a stolen bootstrap ticket before use can impersonate a device, therefore protect delivery and investigate target attestation before high-assurance claims.
3. **Operate:** bind agent ID to one computer, verify key proof on every TLS/session reconnect, validate certificate/revocation/expiry, scope task to that device, and record heartbeat/version/binary hash. Agent validates server identity and each structured task's id, authorization, nonce, expiry, schema and bounds. Tasks queued while offline require expiration and deduplication.
4. **Rotate:** authenticated existing key requests a new device-generated key and short-lived credential with overlap bounded to an approved window; atomically replace active key, revoke old key and audit. Avoid storing reusable passwords on endpoints. Certificate trust store and revocation are enforced by edge/API as described in ARCHITECTURE.md.
5. **Revoke:** authorized admin immediately invalidates identity, disconnects live sessions, cancels or blocks queued tasks and audits. Certificate validation and revocation must be enforced consistently even behind TLS termination.
6. **Reinstall/recovery:** never silently adopt an already enrolled hostname/IP. Revoke or explicitly retire previous key, inspect old deployment history and issue new ticket; reinstall preserving/rotating identity only through an authenticated approved recovery path. A lost key, reimaged host, expired credential or missed rotation needs operator-assisted re-enrollment after verifying device identity. Rate-limit and audit. Offline grace must never permit revoked identities on reconnect.

## Deployment checks and state machine
Resolve target and choose credentials by registered kind (checkout=OKCS; client=GIG) with no trust required. `created -> preflight -> staged -> service_install_or_upgrade -> enrollment -> verification -> succeeded` or explicit `failed / cancelled / needs_reconciliation`; persist every attempt and step. Verify port/DNS, SMB session authentication and ADMIN$ read/write, remote SCM/RPC reachability and permissions, existing service binary/version/hash, staging disk/path/ACL, source and destination digest, service creation/update/configuration and start, service status, bootstrap enrollment and authenticated heartbeat/version/hash. Separate errors for DNS, transport timeout/refused, authentication, share authorization, SCM/RPC/service permission, package/hash, service startup, CA/enrollment and heartbeat. A timeout cannot distinguish firewall from routing or disabled service: report likely causes, not certainty.

Use restricted staging and unique job IDs; securely acquire explicit credentials using APIs without password arguments and isolate incompatible SMB sessions. Upgrade stages and verifies first, keeps known-good files/config, stops gracefully and swaps with journaled recovery. On failure report current service/installation state; attempt safe rollback and verify connectivity, else mark manual recovery required. Reboot/interruption handling must inspect journal and file hashes. Never delete existing working installation pre-validation. WinRM is not a dependency; access to SMB/ADMIN$/SCM and target firewall rules is conditional and must be tested.

## Interactive Session Helper
Agent Windows Service operates in Session 0; a separately packaged per-user/session helper is responsible for displaying the specified Store Commerce warning to the actual interactive operator. Service-to-helper IPC requires user/session-restricted Windows ACLs, authenticated peer and bounded typed messages; helper cannot grant arbitrary tasks or access vault credentials. Report delivery acknowledged, failed or unknown, including no active session. Do not claim dashboard notifications satisfy the local notification requirement. Installation, startup across login/logoff/RDP sessions, integrity, trust and security are untested.
